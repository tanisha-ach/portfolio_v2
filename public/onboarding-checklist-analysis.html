Web vs. Mobile "Getting Started" Patterns — with a focus on RANDOM-ORDER completion

Compiled via Mobbin, 2026-07-31. All screenshots referenced are linked to their canonical Mobbin URL.

Key constraint driving this analysis

The checklist being designed can be completed in any order — no locked steps, no forced sequence. So every example below is evaluated first on how it signals order (or the absence of it), before anything else.

Web vs. Mobile — patterns compared

What web does well:

  • Persistent, low-friction re-entry. Apollo, Vanta, and Loom all keep a permanent nav item or sidebar trigger, so the checklist survives navigation and is never "lost." This matters a lot for a random-order checklist — the user needs to be able to leave and come back to any item without hunting for the entry point.
  • Grouping without forcing sequence. Vanta and Klaviyo both use collapsible category groups, which is a good pattern for a large item count (15–20 tasks) — group by theme, not by required order, and let each group carry its own sub-progress.
  • Richer row real estate. Web rows can carry a description, an icon, and an inline CTA button all in one line (Apollo, Remote), which mobile has to earn back via expand/collapse.

What mobile does well:

  • Expand-in-place instead of navigation. Peloton, Linktree, and Origin all use an accordion pattern — tap a row, it expands inline with description + CTA, no full-screen navigation required. This is the single most reusable pattern for a random-order list: every row behaves identically and independently, which is the free-order signal.
  • Bottom-sheet re-entry. Linktree and Origin surface the checklist as a bottom sheet that can be dismissed and is implied to be re-invokable from a persistent home affordance (a badge or menu item) — lighter-weight than a full dashboard widget.
  • Compact progress framing. A ring ("1/4") or a short segmented bar reads faster at small sizes than a percentage or long bar.

Divergences:

  • Web checklists lean on buttons per row ("Start", "Get Started", "Invite") since there's room; mobile leans on tap-to-expand-then-CTA, keeping the collapsed state to a single line.
  • Mobile is far more likely to gate the checklist behind a separate full-screen entry point reached from a home-tab teaser card (Peloton, Deel) rather than showing the whole thing inline, because vertical space is scarce.
  • Web is more likely to hybridize the checklist with a stepper (Klaviyo's numbered category tabs, Airtable's numbered "what's next") — a pattern that's easy to mistake for a checklist but is actually closer to a wizard. Be careful not to import this pattern by accident.

Random-order handling — the focused section

Products that handle non-linear checklists well

  1. Linktree (iOS) — the strongest example found. Six flat rows, no numbers, no connecting line. Each row is an independent accordion with its own "Skip" link. Critically, the screenshot evidence shows the last item already completed while an earlier item is still open — direct proof the product supports and correctly renders out-of-order completion without visual confusion.
  2. Origin (iOS) — same proof pattern: a circular "1/4" ring (which only communicates count, not position) plus a flat expandable list. Because the ring never implies "step 1 of 4" positionally, the completed item can be anywhere in the list without looking broken.
  3. Deel HR (iOS) — the cleanest visual language: no icons implying progression, no lines, just title + status pill (Done / Not Started). This is probably the simplest pattern to copy if you want minimal design overhead.
  4. Vanta (Web) — good for large item counts. Grouping by theme (not by sequence) with independent per-group fractions lets users tackle whichever category matters to them first, while still giving structure.
  5. Asana (Web) — the 3-card side-by-side layout is an explicit, almost architectural statement that "these are parallel, not sequential" — worth studying for a short (3–5 item) checklist specifically.
  6. Peloton (iOS) — every row's chevron behaves identically regardless of completion state of other rows; the only sequence-like element (the segmented bar) is purely a counter, not a gate.

Specific UI cues that signal "any order" (use these):

  • Flat vertical list, no connecting line between rows
  • No numbers on rows (use checkboxes/circles only)
  • Progress shown as a fraction or ring ("2 of 5"), never as a positional stepper ("Step 2 of 5")
  • Every row's interaction affordance (chevron, button) is identical regardless of position — nothing is greyed out, disabled, or locked
  • Status communicated via pill/badge text ("Done"/"Not started") rather than sequential iconography

Products to NOT copy (they force or imply sequence)

  • Cleo AI (iOS) — numbered pills 1–5, future steps visibly greyed and untappable. This is a linear funnel, not a checklist. Copying this pattern for a random-order feature would actively mislead users into thinking they must go in order.
  • Remote (Web) — uses literal 🔒 lock icons on later items within a group until earlier ones are complete. This is a hard sequence gate, the opposite of what's needed here.
  • N26 (iOS) — vertical checklist connected by a continuous line with a single filled "current step" indicator — classically a progress-tracker visual language (think: shipping tracker), which reads as sequential even if the backend doesn't enforce it. Avoid the connecting-line treatment for this reason.
  • Airtable / Figma Dev Mode (Web) — both use numbered "01/02/03/04" wizards with Back/Next navigation. Not checklists at all — full step gating with no way to jump ahead.
  • Klaviyo (Web) — worth a caveat: the category tabs are freely clickable (good), but the checkmark chain within a category visually implies "do these five in order," even though nothing technically blocks skipping. If you group tasks like this, don't add the connecting checkmark chain — it undercuts the free-order message.

Design recommendations for your random-order checklist

  1. Avoid every sequence cue identified above: no numbers, no connecting/progress lines between rows, no greyed-out/locked future items. Use a flat list where every row's affordance is visually identical regardless of what else is done — model this on Linktree/Deel HR/Peloton, not Cleo AI/Remote/N26.

  2. Show progress as a fraction or ring, never a positional stepper. "3 of 7 complete" or a completion ring communicates how much is left without implying what comes next. Reserve "Step X of Y" language entirely for genuinely linear flows elsewhere in your product.

  3. Let completed items stay visible but visually demoted (checkmark + strikethrough + dimmed, as Linktree and Origin do), rather than removing them from the list or collapsing them out of view. This reinforces that any item was eligible to be done at any time, and gives users a sense of accomplishment without disrupting the list's spatial stability (items shouldn't reflow/reorder on completion, which would undercut the "any order" message by making the list feel sequence-driven).

  4. If you need grouping for a longer list (7+ items), group by theme/category (à la Vanta), not by required order — and give each group its own independent sub-progress rather than a shared checkmark chain. If you do add a chain-style connector within a group, be aware (per the Klaviyo caveat) that it will read as sequential even without a technical gate.

  5. Use the "identical affordance" test before shipping: pick any two rows at random — one done, one not — and confirm their interactive treatment (chevron behavior, button availability, tap target) is otherwise indistinguishable. If a row's interactivity depends on another row's state, that's a Remote/Cleo-style dependency and should be flagged for removal or made explicit as an actual (rare, justified) exception rather than an accident of layout.
